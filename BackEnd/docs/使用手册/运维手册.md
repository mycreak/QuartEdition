## 一、启动

```bash
# 后端
cd BackEnd
python app.py

# 前端（另一个终端）
cd FrontEnd
npm run dev
```

启动顺序：后端先于前端（前端 Vite 代理到 `http://localhost:8000`）。

## 四、Cookie 管理

### 首次设置

Chrome 登录豆瓣后 → F12 → Application → Cookies → 复制 `dbcl2` 和 `bid` 的值。

```bash
# 方式一：管理端 API 替换主账号（推荐）
curl -X POST http://localhost:8000/admin/cookies/replace \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"dbcl2":"xxx","bid":"yyy"}'

# 方式二：文件直接存在 data/douban_storage.json（启动时自动迁移到 data/cookies/）
python scripts/save_cookies.py --dbcl2 "<你的值>" --bid "<你的值>"
```

### 多账号管理（新增）

```bash
# 添加日本备用账号
curl -X POST http://localhost:8000/admin/cookies \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"dbcl2":"xxx","allowed_regions":["JP"],"label":"日本备用"}'

# 查看所有账号
curl http://localhost:8000/admin/cookies -H "Authorization: Bearer $TOKEN"

# 删除账号
curl -X DELETE http://localhost:8000/admin/cookies/main \
  -H "Authorization: Bearer $TOKEN"

# 封禁/恢复
curl -X POST http://localhost:8000/admin/cookies/account_a1b2c3d4/ban \
  -H "Authorization: Bearer $TOKEN"
curl -X POST http://localhost:8000/admin/cookies/account_a1b2c3d4/unban \
  -H "Authorization: Bearer $TOKEN"
```

### 查看状态

```
GET /admin/cookies/status    多账号汇总（活跃/可疑/封禁数）
GET /admin/status            仪表盘 cookie_valid 字段
```

### Cookie 过期判断

日志中出现 `豆瓣登录态已过期` → 需要重新获取 Cookie。Cookie 有效时，启动日志显示 `豆瓣登录态验证通过 ✅`。

## 五、代理管理

```bash
# 查看所有代理
curl http://localhost:8000/admin/proxies -H "Authorization: Bearer $TOKEN"

# 添加代理
curl -X POST http://localhost:8000/admin/proxies \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"host":"1.2.3.4","port":3128,"region":"CN"}'

# 删除代理
curl -X DELETE http://localhost:8000/admin/proxies/1.2.3.4/3128 \
  -H "Authorization: Bearer $TOKEN"

# 手动全量验证
curl -X POST http://localhost:8000/admin/proxies/health-check \
  -H "Authorization: Bearer $TOKEN"
```

代理状态机：`UNKNOWN → ALIVE ↔ SUSPICIOUS → BANNED`。连续失败 2 次自动封禁。管理员手动封禁用 DELETE 端点。

## 七、已知风险

### 7.1 hypercorn reloader 导致间歇 401（已修复）

**现象**：密码正确但 `POST /auth/login` 返回 401。重启后恢复。

**根因**：`use_reloader=True` 时，文件变更触发 worker fork，DB 连接池/全局变量可能在初始化一半时接收到请求。

**修复**：`app.py` 中 `config.use_reloader = False`。开发时手动 `Ctrl+C` 重启。

### 7.2 DB 连接类型污染导致 401（2026-05-10 ContextVar 根除）

**现象**：密码正确但 `POST /auth/login` 返回 401，`/admin/movies` 等接口间歇性 401。日志显示 `用户名 'admin1' 不存在`。

**根因**：`DatabaseLayerV2` 的 `_database_type` 是普通 Python 属性（共享可变状态）。`review_service.py` 在 `set_database("mongodb")` 之后 `await self.db.find(...)` 期间出让事件循环，其他请求读取到 `MONGODB` 类型 → `users` 表查询走 MongoDB 驱动 → 返回 None → 401。

```
请求 A (list_comments):              请求 B (login):
  set_database("mongodb")              ┌─ await 出让
  await self.db.find(...) ──────────→  │  _database_type=MONGODB
                                       │  db.find_one("users", ...)
                                       │  → MongoDB 查询 → None
                                       │  → "用户名不存在" → 401
  set_database(MySQL)  ← 恢复
```

**修复**（2026-05-10）：`_database_type` 改为 `contextvars.ContextVar` — 每个 asyncio 任务持有独立的类型副本，A 切换到 MongoDB 不影响 B 读取 MySQL。

```python
# db/database_v2.py
class DatabaseLayerV2:
    def __init__(self):
        self._database_type = contextvars.ContextVar("db_type", default=None)

    def _get_type(self): return self._database_type.get()
    def _set_type(self, v): self._database_type.set(v)
```

**影响**：彻底消除并发竞态。不再需要在 review_service 中做 save/restore（ContextVar 自动隔离），但保留 restore 逻辑以支持同一请求内多数据库切换。

### 7.3 pymongo DEBUG 日志噪声（2026-05-09 已修复）

`utils/logging_config.py` 中 `pymongo` 日志级别设为 WARNING，不再输出每 10s 的 heartbeat 日志。

### 7.4 Task History 时间丢失时区（2026-05-09 已修复）

`datetime.isoformat()` → `to_iso()`，输出带 `+08:00` 后缀。

### 7.5 Worker 同时执行导致豆瓣反爬（2026-05-09 已修复）

5 Worker 抢到任务后瞬间并发 → 豆瓣检测到异常。修复：Worker sleep 2~5min，自然错峰。

### 7.6 CookieManager 激活（2026-05-10）

**变更**：`app.py` 启动时调用 `init_cookie_manager()`，此前日志输出 `RuntimeError: CookieManager 未初始化` 的问题消失。

**影响**：
- `IdentityManager` 正常就绪，爬虫身份绑定可用
- 旧版管理 API `POST /admin/cookies/replace` 向下兼容，内部委托给 `CookieManager.add_account("main")`
- `data/douban_storage.json` 在首次初始化时自动迁移到 `data/cookies/account_main.json`

### 7.7 movie_scrape_task 拆分（2026-05-10）

**变更**：`movie_scrape_task` 不再爬取 celebrities 页，改为 `save_movie_basic()` 以原子事务写入基础信息，然后自动注入 `director_crawl` 子任务。

**影响**：
- 现有 movie_scrape_task 响应时间从 ~8s 降至 ~4s
- `director_crawl` 可在失败管理面板独立重试
- 未完成前 `GET /user/movies/<id>` 返回的 `directors/actors/crew` 为空列表，
  前端应显示"演职人员信息暂缺"而非报错

## 八、性能指标参考

| 指标 | 正常范围 | 异常信号 |

## 九、优雅关闭

服务收到 `SIGTERM` 时的关闭顺序：

```
1. stop_puller()           停止拉取
2. stop_browser_pool()     等待 in-flight Worker（30s 超时）
3. drain_task_queue()      队列中未消费的任务写回 Redis ZSET
4. stop_monitor()          停止事件消费
5. close_db()              MySQL / MongoDB / Redis 关闭
```
