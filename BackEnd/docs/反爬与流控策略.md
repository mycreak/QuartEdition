## 一、策略分层

```
Layer 1: 提交冷却          Layer 2: Puller 节流          Layer 3: 并发控制          Layer 4: 反反爬
(task_cooldown_seconds)   (背压 + 退避)                  (Semaphore)               (Worker休眠+浏览模拟)

POST → ZSET score 错开    Puller 不过度拉取              Browser 最多 N 并行       Worker 执行后 sleep
                                                                                    Playwright 内模拟人
```

## 二、Layer 1 — 提交冷却（ZSET score 错开）

### 位置

[crawler/subtask.py](../crawler/subtask.py#L82-L85) → [db/database_v2.py](../db/database_v2.py#L588-L604)

### 机制

```python
execute_at = max(now, last_submit_time + cooldown_seconds)
```

每次任务提交时计算 `score = max(当前时间, 上一次提交时间 + 2s)`，作为 Redis ZSET 的 score。

### 效果

```
提交时间线：
  任务A: 10:00:00.000 → execute_at = 10:00:00.000
  任务B: 10:00:00.300 → execute_at = 10:00:02.000  ← 被推到 +2s
  任务C: 10:00:00.600 → execute_at = 10:00:04.000
  任务D: 10:00:03.000 → execute_at = 10:00:04.000  ← 自然错开到 +2s

→ ZSET 内相邻 score 至少差 2s
→ Puller 按 score 到期拉取，自然间隔 ≥2s
```

### 配置

| 参数 | 默认值 | .env 变量 |
|---|---|---|
| `task_cooldown_seconds` | 2s | `PULLER_TASK_COOLDOWN_SECONDS` |

## 三、Layer 2 — Puller 节流

### 位置

[background/puller.py](../background/puller.py)

### 3a. 背压（Backpressure）

当 asyncio.Queue 积压过多时，Puller 暂停拉取，等 Worker 消化。

```
高水位: qsize ≥ 80% maxsize → 暂停拉取，sleep(0.5s)
低水位: qsize ≤ 60% maxsize → 恢复拉取（回滞防止抖动）
```

**为什么需要回滞**：防止在 80% 线附近反复开关造成的抖动。

### 3b. 空队列退避（Backoff）

当 Redis ZSET 无到期任务时，Puller 指数增长休眠间隔。

```
有任务领取 → sleep = base_sleep (0.1s)
无任务      → sleep = min(sleep × 1.5, max_sleep)
              sleep: 0.1s → 0.15s → 0.225s → 0.337s → ... → 5s (上限)
```

### 配置

| 参数 | 默认值 | .env 变量 |
|---|---|---|
| `base_sleep` | 0.1s | `PULLER_BASE_SLEEP` |
| `max_sleep` | 5.0s | `PULLER_MAX_SLEEP` |
| `backpressure_sleep` | 0.5s | `PULLER_BACKPRESSURE_SLEEP` |
| `batch_size` | 10 | `PULLER_BATCH_SIZE` |

## 四、Layer 3 — 并发控制（Browser Semaphore）

### 位置

[crawler/__init__.py](../crawler/__init__.py#L124) — 信号量定义
[crawler/__init__.py](../crawler/__init__.py#L166-L178) — 包装方法

### 动机

Worker cooldown 解决的是"同一 Worker 连续请求"的问题，但不解决"5 个 Worker 同时发起 Playwright 请求"的问题。如果 5 个 Worker 恰好同时执行 browser 任务并使用同一代理 IP，豆瓣会看到同一 IP 的 5 个并发 Playwright 实例，极易触发风控。

### 机制

```python
# 初始化
self._browser_sem = asyncio.Semaphore(browser_concurrency)  # 默认 2

# 包装方法 — 所有 browser 调用统一走这里
async def _browser_fetch(self, url):
    async with self._browser_sem:
        return await self._browser.fetch(url)

async def _browser_fetch_page(self, url, identity=None):
    async with self._browser_sem:
        return await self._browser.fetch_page(url, identity)
```

### 效果

```
5 个 browser 任务同时到期：

Semaphore(2) 限制：
  Worker-0 → _browser_fetch → 拿到信号量 ✅ → 执行
  Worker-1 → _browser_fetch → 拿到信号量 ✅ → 执行
  Worker-2 → _browser_fetch → 等待信号量 ⏳
  Worker-3 → _browser_fetch → 等待信号量 ⏳
  Worker-4 → _browser_fetch → 等待信号量 ⏳

Worker-0 完成 → 释放信号量 → Worker-2 进入
Worker-1 完成 → 释放信号量 → Worker-3 进入

→ 豆瓣看到：同一 IP 最多 2 个并发
→ 配合 Worker cooldown → 实际请求间隔 75~125s
```

### 配置

| 参数 | 默认值 | .env 变量 |
|---|---|---|
| `browser_concurrency` | 2 | `CRAWLER_BROWSER_CONCURRENCY` |

`browser_concurrency=1` 即串行模式。

## 五、Layer 4a — Worker 执行后休眠（反爬错峰核心）

### 位置

[background/worker.py](../background/worker.py#L353-L358)

### 机制

每个 Worker 在 `execute(task)` 完成后、取下一个任务前，随机休眠。

```python
cooldown = random.uniform(
    puller_config.worker_rest_min,   # 150.0s
    puller_config.worker_rest_max,   # 250.0s
)
await asyncio.sleep(cooldown)
```

### 为什么有效

5 个 Worker 各自独立、互不知情，随机值天然错峰：

```
Worker-0 完成 → random(150,250) = 168s → 168s 后取下一个
Worker-1 完成 → random(150,250) = 213s → 213s 后取下一个
Worker-2 完成 → random(150,250) = 182s → 182s 后取下一个
Worker-3 完成 → random(150,250) = 241s → 241s 后取下一个
Worker-4 完成 → random(150,250) = 155s → 155s 后取下一个

→ 5 个 Worker 的下次请求分散在 155~241s
→ 豆瓣看到的模式：每隔 10~50s 来一个请求
```

### 休眠期间行为

- 不持任务（`task_done()` 已调用）
- 不计 busy（`_busy_counter` 已减）
- Puller 可继续拉新任务到 Queue

### 配置

| 参数 | 默认值 | .env 变量 |
|---|---|---|
| `worker_rest_min` | 150s | `PULLER_WORKER_REST_MIN` |
| `worker_rest_max` | 250s | `PULLER_WORKER_REST_MAX` |

## 六、Layer 4b — 浏览模拟（Playwright 内人类行为）

### 位置

[crawler/fetcher.py](../crawler/fetcher.py#L347-L393)

### 机制

每个 `_do_fetch()` 调用在 `networkidle` 后、`page.content()` 前，自动执行一段随机化的人类浏览模拟：

```
① 随机初始等待 1~3s              — 模拟阅读
② 检测 #sub 按钮 → 点击 + 等 2~5s  — 自动过豆瓣验证
③ scrollTo(bottom, smooth)       — 触发懒加载
   等 1.5~3s
④ scrollBy(-400~900)             — 向上回滚
   等 0.8~1.8s
⑤ scrollBy(-200~600)             — 再回滚一段
   等 0.5~1.5s
⑥ scrollBy(+200~500)             — 滚回中间位置
   等 0.5~1.0s
```

### 为什么有效

- 纯 `asyncio.sleep(10)` = "打开页面 → 发呆 10s → 突然离开" → 极易被风控判定
- 滚动 + 随机等待 = "打开 → 浏览 → 回看 → 再浏览" → 类人浏览轨迹
- `smooth` 行为 + 随机步长 → 每次轨迹不同，无固定模式

### 设计保证

- 失败不影响主流程（`except Exception: pass`）
- 对所有 Playwright 任务生效（`_do_fetch` 内部调用）
- `review_body_crawl` 有自己独立的浏览模拟（`_do_fetch_review_body`），互不干扰

## 八、全链路聚合效果

```
任务A 提交 (score=00s)  →  Puller 00s拉取 → Queue → Worker-0 00s取
                           ├─ Semaphore 准入 → Playwright fetch（含浏览模拟 ~10s）
                           └─ 30s 完成 → sleep 168s

任务B 提交 (score=02s)  →  Puller 02s拉取 → Queue → Worker-1 02s取
                           ├─ Semaphore 准入（与 Worker-0 并发 OK）
                           └─ 35s 完成 → sleep 213s

任务C 提交 (score=04s)  →  Puller 04s拉取 → Queue → Worker-2 04s取
                           ├─ Semaphore 等待 Worker-0 释放
                           └─ Worker-0 释放 → Worker-2 进入 → ... → sleep 182s

...

Worker-0 168s 后醒来 → Semaphore 空闲 → 取下一个 → 距离上次同一 Worker 请求 = 168s
                     距离上次豆瓣收到的请求 = 取决于其他 Worker 是否在工作

→ 最差情况：同一 IP 最多同时 2 个 Playwright 实例
→ 平均情况：同一 IP 请求间隔 ≥ 60s
```

## 九、配置速查

### .env 变量一览

```bash
# Layer 1 — 提交冷却
PULLER_TASK_COOLDOWN_SECONDS=2

# Layer 2 — Puller 节流
PULLER_BASE_SLEEP=0.1
PULLER_MAX_SLEEP=5.0
PULLER_BACKPRESSURE_SLEEP=0.5
PULLER_BATCH_SIZE=10

# Layer 3 — 并发控制
CRAWLER_BROWSER_CONCURRENCY=2
CRAWLER_API_CONCURRENCY=5

# Layer 4 — Worker 休眠
PULLER_WORKER_REST_MIN=150
PULLER_WORKER_REST_MAX=250
```

### 调优建议

| 场景 | 建议 |
|---|---|
| 被豆瓣频繁风控 | `CRAWLER_BROWSER_CONCURRENCY=1` + `WORKER_REST_MAX=300` |
| 吞吐优先 | `BROWSER_CONCURRENCY=3` + `WORKER_REST_MIN=120` |
| 纯 api 任务（无浏览器） | 不受 `BROWSER_CONCURRENCY` 影响，受 `API_CONCURRENCY` 限制 |
