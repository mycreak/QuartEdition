# BrowserPool / Crawler / BrowserFetcher 协同工作机制

> 从任务取走到页面资源释放的完整链路
> 最后更新：2026-05-07
> 相关文件：`background/worker.py` / `crawler/__init__.py` / `crawler/fetcher.py` / `crawler/config/crawler_config.py`

## 一、总体架构

```
┌──────────────────────────────────────────────────────────────────────┐
│                         app.py                                       │
│                                                                      │
│  browser = await p.chromium.launch()        ← 1 个 Chromium 进程    │
│  init_crawler(browser, movie_service, ...)  ← 注入给 Crawler        │
│                                                                      │
│  BrowserPool(                                                       │
│    task_queue=q,           ← Puller 写入任务的队列                   │
│    execute_func=crawler.execute,  ← ★ 回调注入点                    │
│    event_queue=eq,         ← Monitor 消费事件                        │
│    worker_count=5                                                  │
│  )                                                                  │
└──────────────────────────────────────────────────────────────────────┘
           │                              │
           │ 5 个 Worker                    │ 1 个 BrowserFetcher (全局单例)
           │ 协程                          │ 内嵌 Playwright Browser
           ▼                              ▼
┌──────────────────────┐    ┌──────────────────────────────────────────┐
│    BrowserPool       │    │         BrowserFetcher                   │
│                      │    │                                          │
│  _worker_loop(0) ────┼───▶│ _do_fetch(url, proxy?)                 │
│  _worker_loop(1) ────┼───▶│   new_context(user_agent, proxy, ...)   │
│  _worker_loop(2) ────┼───▶│   new_page()                            │
│  _worker_loop(3) ────┼───▶│   page.goto(url, networkidle)           │
│  _worker_loop(4) ────┼───▶│   page.content() → html                 │
│                      │    │   finally: page.close() + ctx.close()    │
│                      │    │   崩了 → _restart_browser() 自愈         │
└──────────────────────┘    └──────────────────────────────────────────┘
           │                              │
           │ execute(task)                 │ html
           ▼                              ▼
┌──────────────────────────────────────────────────────────────────────┐
│                       Crawler 引擎                                    │
│                                                                      │
│  execute(task_str)                                                   │
│    → task.type 分发                                                  │
│    → parser.parse_*  (纯函数，不依赖 IO)                              │
│    → storage.save_*  (MySQL / MongoDB)                               │
└──────────────────────────────────────────────────────────────────────┘
```

**三层协作合约**：

| 层                  | 输入                  | 输出                  |             资源所有权            |
| ------------------ | ------------------- | ------------------- | :--------------------------: |
| **BrowserPool**    | `task_queue.get()`  | `event_queue.put()` |         Task 协程（5 个）         |
| **Crawler**        | `execute(task_str)` | 抛异常 / 正常返回          |            无（纯调度）            |
| **BrowserFetcher** | `fetch(url)` → html | `return html`       | page + context（在 finally 释放） |

关键约束：**BrowserPool 不碰浏览器，Crawler 不碰 page/context，BrowserFetcher 不碰任务调度**。

## 二、BrowserPool — 5 个纯调度 Worker

### 2.1 设计定位

BrowserPool 是**纯调度器**，它做的事只有三件：

```
① queue.get()  → 取任务
② execute(task)   → 调外界注入的函数
③ event_queue.put() → 上报结果
```

**为什么不持有浏览器？** 浏览器资源（page、context）生命周期由 `BrowserFetcher` 内部管理。如果 BrowserPool 也持有，会出现双层资源嵌套，谁负责释放就说不清了。

### 2.2 并发模型：5 Worker 共享 1 Chromium

```
Worker-0 ──→ execute(task_A) ──→ BrowserFetcher.fetch(url) ──→ new_context() → page_A
Worker-1 ──→ execute(task_B) ──→ BrowserFetcher.fetch(url) ──→ new_context() → page_B
Worker-2 ──→ execute(task_C) ──→ BrowserFetcher.fetch(url) ──→ new_context() → page_C
Worker-3                                                         idle
Worker-4                                                         idle
                         ↑
              所有 Worker 共享 1 个 browser 实例
              每个 Worker 独立创建自己的 context + page
```

`BROWSER_SEMAPHORE = asyncio.Semaphore(2)` 限制同时最多 2 个 Worker 在 fetch 详情页。原因是爬取一部电影需要 2 次 BrowserFetcher（详情页 + /celebrities 页），2 并发每部电影占用 \~3.7s × 2 = \~7.4s。

### 2.3 结果上报

Worker 不关心任务是 movie\_crawl、review\_crawl 还是 comment\_crawl——只区分三种结果：

```python
WorkerEvent(event_type=SUCCESS)    # execute 正常返回 → 计数
WorkerEvent(event_type=FAILURE,    # execute 抛异常 → 写 MySQL + WS 推送
            kind=classify_exception(e),
            reason=str(e))
WorkerEvent(event_type=CANCELLED)  # Worker 被 cancel → 写 MySQL + WS 推送
```

## 三、Crawler — 任务分发与编排

### 3.1 模块级单例

Crawler 用**模块级全局变量**储存 4 个依赖（非 `class` 模式）：

```python
# crawler/__init__.py — 模块级状态
_api_fetcher:    Optional[ApiFetcher]    = None
_browser_fetcher: Optional[BrowserFetcher] = None
_movie_service:  Any = None
API_SEMAPHORE:    asyncio.Semaphore = None
BROWSER_SEMAPHORE: asyncio.Semaphore = None

def init_crawler(browser, movie_service, cookies=None, playwright=None):
    """由 app.py 在启动时调用，注入双引擎 + MovieService"""
    global _api_fetcher, _browser_fetcher, _movie_service
    _api_fetcher = ApiFetcher(cookies=cookies)
    _browser_fetcher = BrowserFetcher(browser=browser, playwright=playwright, ...)
    _movie_service = movie_service
    API_SEMAPHORE = asyncio.Semaphore(5)       # 评论正文 API 并发
    BROWSER_SEMAPHORE = asyncio.Semaphore(2)    # 详情页并发
```

### 3.2 `execute(task)` 签名合约

```python
async def execute(task: str) -> None:
    """
    成功：正常返回（不返回值）
    失败：抛异常（由 BrowserPool._worker_loop 捕获 → classify → 上报）
    """
```

### 3.3 任务分派

```
execute(task_str)
  │
  ├─ type == "movie_crawl"
  │  ① ApiFetcher.fetch(榜单API)        → double_id 列表
  │  ② asyncio.gather(                  BROWSER_SEMAPHORE=2
  │       _fetch_and_parse_one × N:
  │         BrowserFetcher.fetch(详情页)  → parse_movie_detail  (v:微格式)
  │         BrowserFetcher.fetch(celebrities) → parse_personnel  (7种角色)
  │         → 合并为 detail dict
  │     )
  │  ③ save_movies(movie_service, details)  → MySQL 8表
  │
  ├─ type == "review_crawl"
  │  ① BrowserFetcher 翻页(2页) → parse_review_list
  │  ② asyncio.gather(            API_SEMAPHORE=5
  │       ApiFetcher.fetch(/j/review/{id}/full) × 40条
  │     ) → parse_review_full
  │  ③ save_reviews → MongoDB
  │
  └─ type == "comment_crawl"
     ① BrowserFetcher 翻页(5页) → parse_comments
     ② save_comments → MongoDB
```

### 3.4 并发控制

| Semaphore           |  值  | 适用场景                | 原因                                |
| ------------------- | :-: | ------------------- | --------------------------------- |
| `BROWSER_SEMAPHORE` |  2  | 影评详情页/celebrities 页 | 1 个 Chromium + 5 Worker，限制并发防内存爆炸 |
| `API_SEMAPHORE`     |  5  | 长评正文 API            | aiohttp 轻量连接，可以高并发                |

## 四、BrowserFetcher — 浏览器资源全生命周期

### 4.1 核心契约：每次 fetch 自包含

```
BrowserFetcher.fetch(url):

  ┌─ new_context(user_agent, proxy, viewport, storage_state) ─┐
  │  new_page()                                                │
  │  add_init_script(disable webdriver)                        │
  │  page.goto(url, networkidle)                               │
  │                                                            │
  │  if "sec.douban.com" in page.url:                          │
  │    wait 3s → 等待 SHA-512 挑战完成                         │
  │                                                            │
  │  html = page.content()                                     │
  │                                                            │
  │  if len(html) < 200 or "检测到有异常请求" in html:         │
  │    return (html, False)                                    │
  │  return (html, True)                                       │
  │                                                            │
  └─ finally: page.close() + context.close() ──────────────────┘
```

**关键设计**：每次 `fetch()` 创建**全新的** `BrowserContext` 和 `Page`，用完在 `finally` 中关闭。不跨请求复用 context——不同代理、不同 Cookie 状态需要隔离。

### 4.2 崩溃自愈

```python
class BrowserFetcher:
    _restart_lock = asyncio.Lock()

    async def _restart_browser(self):
        async with self._restart_lock:          # ★ 5 Worker 同时检测到崩溃 → 只有一个重启
            if self.browser.is_connected():     # ★ 双检：等锁期间可能已被其他 Worker 重启
                return
            await self.browser.close()
            self.browser = await self._playwright.chromium.launch(headless=True)

    # _do_fetch 的 exception handler:
    except Exception:
        if not self.browser.is_connected():     # 浏览器崩了 → 自愈
            await self._restart_browser()
        return "", False                        # 本次 fetch 失败 → 外层走代理重试/直连兜底
```

### 4.3 代理链

```
fetch(url):
  有代理池:
    for attempt in range(3):
      proxy = pool.get_proxy()       → 取代理
      html, ok = _fetch_via_proxy()  → 通过代理请求
      if ok: pool.report_success() → return
      else:   pool.report_failure() → 切下一个代理

  代理全失败 / 无代理池:
    _fetch_direct()                  → 直连兜底
```

### 4.4 反爬策略

```
① user_agent: Chrome/125 → 不装扮移动端
② viewport: 1920×1080    → 标准桌面分辨率
③ init_script: Object.defineProperty(navigator, 'webdriver', {get: () => undefined})
④ wait_until: "networkidle" → SHA-512 JS 自动执行完成
⑤ sec.douban.com 检测: 检测到跳转 → wait 3s → 等待重定向回原页面
⑥ HTML 反爬标记: "检测到有异常请求" → 视为失败 → 切代理重试
```

## 五、完整任务执行链（P1 重构后）

### 5.1 movie\_crawl — 补充 douban\_id 资产

```
admin POST /admin/tasks {type: movie_crawl, type_num: 11, interval_id: "100:90"}
  → add_delayed_task_with_limit() → ZADD delay_queue (cooldown=2s)

──── Puller 弹出到期任务 ────

Worker 拿到 movie_crawl 任务
  ├─ ① 查 crawl_progress.douban_total（有则跳过 count API）
  │    → 无缓存: ApiFetcher.fetch(top_list_count) → total=50
  ├─ ② COUNT douban_ids WHERE type_num AND interval_id → start 偏移
  ├─ ③ ApiFetcher.fetch(top_list?start=N&limit=20)
  │    → parse_movie_list → 20 个 {douban_id, title}
  ├─ ④ INSERT IGNORE douban_ids（不创建子任务，纯入库）
  └─ ⑤ event_queue.put(SUCCESS) → task_history=done
```

**done 语义**：榜单 API 成功 + douban\_id 已入库。进度在 `GET /admin/tasks` 中通过 `douban_total` vs `douban_ids` 实际入库数展示。

### 5.2 movie\_scrape\_task — 单部电影爬取（解耦后）

管理员从 douban\_ids 表认领一个 ID 后，显式指定 cookie\_id + proxy\_key 提交：

```
admin POST /admin/tasks {type: movie_scrape_task, douban_id: "1292052", cookie_id: "main", proxy_key: "1.2.3.4:3128"}
  → ZADD → Puller → Worker

Worker 拿到 movie_scrape_task 任务
  ├─ ① IdentityManager.resolve(cookie_id, proxy_key) → Identity
  │     检查: account.allowed_regions 是否包含 proxy.region
  ├─ ② BrowserFetcher.fetch_page(detail_url, identity) × 3 次重试
  │     → parse_movie_detail(html)
  ├─ ③ save_movie_basic() — 原子事务写入（无演职人员）
  │     BEGIN TRANSACTION
  │       INSERT movies (基础信息)
  │       INSERT movie_genres × N
  │       INSERT movie_regions × M（region 不存在则自动创建）
  │       INSERT movie_ratings
  │     COMMIT  ← 全成功或全回滚
  ├─ ④ UPDATE douban_ids SET is_acquired=1, task_id=...
  ├─ ⑤ 自动 ZADD director_crawl 子任务 + INSERT task_history(admin_id=父任务提交人)
  └─ ⑥ event_queue.put(SUCCESS) → task_history=done

──── Puller 弹出 director_crawl 子任务 ────

另一个 Worker 领取 director_crawl 任务
  ├─ ① BrowserFetcher.fetch_page(celebrities_url) → HTML
  ├─ ② parse_personnel(html) → [{name, douban_id, role_type}, ...]
  ├─ ③ save_crew(movie_id, crew) — 原子事务写入
  │     BEGIN TRANSACTION
  │       INSERT people × K（幂等：按 douban_id 或 name 去重）
  │       INSERT movie_credits × K
  │     COMMIT  ← 全成功或全回滚
  └─ ④ event_queue.put(SUCCESS) → task_history=done
```

**失败隔离**：

```
详情页 3 次重试全失败:
  → movie_scrape_task 失败（FetcherError）
  → task_failures(scope='batch') + WS 推送给提交者
  → 管理员点"重爬" → 从头重爬（详情页 + 自动子任务）

详情页成功、入库成功、子任务顺利注入:
  → movie_scrape_task = done ✅
  → director_crawl 子任务 = submitted
  → 子任务失败 → task_failures(scope='item', admin_id=父任务提交人, item_douban_id='1292052')
  → 管理员在失败管理面板看到这条失败
  → 点"重爬" → 只重跑 celebrities 页，不重跑详情页
```

## 六、review\_crawl 长短评抓取（解耦模式 — 类比电影 douban_ids）

长评抓取分层为两步，与电影抓取（douban_ids → movie_detail_crawl）完全同构：

```
┌─ Step 1: 摘要采集 review_crawl ──────────────────────────────────┐
│  BrowserFetcher → subject/{id}/reviews?start=N（~3.5s/页）        │
│  → parse_review_list → review_id + title + author + date        │
│  → INSERT IGNORE movie_review（MySQL 中间表，幂等）               │
│                                                                 │
│  中间表：                                                         │
│    movie_review(review_id PK, movie_id, subject_id,              │
│                 title, author, useful_count, date, status)      │
│    status: pending | done | failed                              │
│    可观测性：SELECT COUNT(*) WHERE movie_id=N AND status='pending'│
└─────────────────────────────────────────────────────────────────┘
         │
         ▼  movie_review 表（中间态，可断点续爬、可逐条重试）
         │
┌─ Step 2: 正文爬取 review_body_crawl ────────────────────────────┐
│  ApiFetcher → /j/review/{review_id}/full（JSON API，~0.3s/条）   │
│  → parse_review_full → 纯文本正文（丢弃 img 标签）               │
│  → MongoDB reviews.upsert_review（幂等）                         │
│  → UPDATE movie_review SET status='done'                        │
│                                                                 │
│  失败隔离：单篇正文 API 挂 → status='failed'，不影响同批次其他      │
│  重爬粒度：只需对 status='failed' 的 review_id 重新 ZADD         │
└─────────────────────────────────────────────────────────────────┘
```

**设计动机**：

| 维度 | 旧（合并模式） | 新（解耦模式） |
|------|:---:|:---:|
| Worker 占用 | 1 Worker 独占列表+正文全程（~30s） | 列表完成后 Worker 立即释放 |
| 正文失败重爬 | 整批重新提交 review_crawl | 仅对 failed 的 review_id 逐条重爬 |
| 进度可视 | 无中间态，只有最终入库数 | movie_review 表实时显示 pending/done |
| 正文 API 调用 | `asyncio.gather` 并发，Worker 内阻塞 | ApiFetcher 独立调度，5 Worker 并发认领 |
| 断点续爬 | ❌ 不支持 | ✅ movie_review 已入库的 review_id 跳过 |

### 6.1 review\_crawl — 摘要采集（Layer 1）

**输入**：`{type: "review_crawl", subject_id, movie_id, review_pages}`

**数据流**：

```
for page_num in range(review_pages):
    html = BrowserFetcher.fetch(subject/{id}/reviews?start=N)
    meta_list = parse_review_list(html) → [{review_id, title, author, date, useful_count}, ...]
    去重后 INSERT IGNORE movie_review (status='pending')
    翻页异常 → logger.error + continue
```

**去重**：`INSERT IGNORE` 利用 `review_id` 主键天然防重复；跨批次再跑同一电影不会产生脏数据。

### 6.2 review\_body\_crawl — 正文爬取（Layer 2，新增任务类型）

**输入**：`{type: "review_body_crawl", subject_id, movie_id, max_count: 20}`

**数据流**：

```
SELECT review_id, title, author, date, useful_count
FROM movie_review
WHERE movie_id = N AND status = 'pending'
LIMIT max_count

for each pending review:
    ApiFetcher.fetch(/j/review/{review_id}/full)
    parse_review_full → 纯文本正文
    MongoDB upsert_review(review_id, subject_id, body_dict, movie_id)
    UPDATE movie_review SET status='done'
    单篇失败 → _report_item_failure(scope='item') → status='failed'
```

**执行模型**：`review_body_crawl` 内部串行调用 ApiFetcher（~0.3s/条），20 条约 6s。可重复提交多个任务，Worker 并发认领。

### 6.3 comment\_crawl — 短评抓取（不变）

短评无需二次 API → 不拆解，保持单一任务 `comment_crawl` 翻页+解析+写入全部串行。

### 6.4 容错与恢复

```
摘要列表翻页失败（review_crawl）:
  logger.error → continue 下一页
  失败页数据永久丢失 → 重新提交 review_crawl 即可（INSERT IGNORE 幂等）

正文 API 失败（review_body_crawl）:
  _report_item_failure(scope='item') → task_failures
  UPDATE movie_review SET status='failed'
  管理员在 /admin/failures 看到 scope='item' 的失败 → 点重试
  或在爬虫面板提交新的 review_body_crawl（自动跳过 done，只爬 pending）

短评翻页失败（comment_crawl）:
  logger.error → continue → 失败页数据永久丢失
  _report_item_failure(scope='item') → task_failures

## 七、关键设计决策

| 决策                                 | 原因                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------- |
| **BrowserFetcher 自管 page/context** | BrowserPool 不持有浏览器资源 → 职责清晰 → finally 释放有确定性                                  |
| **每次 fetch 新建 context**            | 不同代理需独立 context；豆瓣 Cookie 隔离；context 泄漏一次只丢一个                                 |
| **崩溃自愈用 asyncio.Lock**             | 5 Worker 同时检测到崩溃 → 只有第一个重启，其余等锁                                               |
| **BROWSER\_SEMAPHORE=2**           | 5 Worker 但只允许 2 个同时跑 BrowserFetcher（1 个 Chromium 内核，多 tab 内存 \~200MB/context） |
| **Crawler 用模块级单例而非类**              | 减少样板；所有 Worker 共享同一个 browser 引用（Chromium 进程开销大）                               |
| **Crawler.execute 抛异常即失败**         | Worker 用 try/except 捕获 → classify\_exception → 种类级重试决策                        |
| **MovieService 注入而非每个函数传**         | 省参数；模块级 `_movie_service` 全局共享，避免业务参数污染 execute 签名                             |
| **解析与获取严格分层**                      | `parse_*` 全纯函数 → 单元测试不需要 API/浏览器 → mock 成本低                                   |

    │         1 个 Chromium 进程            │
    │    BrowserFetcher (共享 browser)     │
    │    ┌─ context_A ─ page_A            │
    │    ├─ context_B ─ page_B            │
    │    └─ ... (每 fetch 独立)           │
    └─────────────────────────────────────┘
```

***

## 九、异常流转

```
BrowserFetcher.fetch() 失败:
  → FetcherError("直连返回异常" / "代理全失败")
  → Crawler._handle_movie_crawl 的 try/except 捕获
  → _report_item_failure (写 task_failures 的 item scope)
  → continue (不阻塞整批)

Crawler.execute() 失败:
  → BrowserPool._worker_loop 的 except Exception 捕获
  → classify_exception(e)  → 判断可重试性
  → event_queue.put(WorkerEvent(FAILURE))
  → Monitor._drain_events() → INSERT task_failures
  → 返回 idle 状态，开始取下一个任务

BrowserFetcher 崩溃:
  → _do_fetch 的 except Exception: is_connected() == False
  → _restart_browser()  (asyncio.Lock 串行化)
  → 本次 fetch 返回 ("", False)
  → 外层代理轮换或直连兜底
```
