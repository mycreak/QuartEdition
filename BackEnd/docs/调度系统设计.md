# 后台调度系统设计

> Puller → Queue → Worker → Crawler → Queue → Monitor — 三组件异步流水线
> 最后更新：2026-05-30

---

## 一、系统总览

### 1.1 三组件流水线架构

调度系统由三个独立协程组成，通过两个 `asyncio.Queue` 彻底解耦：

```
                   ┌─────────────────────────────────────────────────────┐
                   │                   调度系统全景图                       │
                   └─────────────────────────────────────────────────────┘

  Redis ZSET             asyncio.Queue            asyncio.Queue          MySQL / MongoDB
  (延迟队列)              (任务通道)              (事件通道)            (持久化)
 ┌──────────┐   任务    ┌──────────┐   任务     ┌───────────┐   事件    ┌──────────────┐
 │ 到期任务  │ ───────→ │  任务队列  │ ───────→  │ BrowserPool│ ───────→ │   Monitor     │
 │          │           │ (桥梁)   │           │  (N个Worker)│         │  (消费事件)  │
 └──────────┘           └──────────┘           └───────────┘          └──────────────┘
       ↑                                             │                       │
       │                                             │                       │
   Puller                                        Crawler                  WebSocket
 (ZPOP+ZADD)                                  (纯业务逻辑)                (管理员推送)
```

### 1.2 角色定义

| 组件 | 文件 | 职责 | 运行时形态 | 类比 |
|------|------|------|-----------|------|
| **Puller** | [background/puller.py](../background/puller.py) | 从 Redis ZSET 拉取到期任务 → 放入任务队列 | 单个协程 | **进货员** |
| **BrowserPool** | [background/worker.py](../background/worker.py) | 从任务队列取任务 → 调用 Crawler 执行 → 上报事件 | N 个协程 (默认 5) | **加工车间** |
| **Monitor** | [background/monitor.py](../background/monitor.py) | 消费事件队列 → 写入 MySQL + 采集指标 + WS 推送 | 单个协程 | **质检+报告员** |

### 1.3 核心数据流

```
管理员 POST /admin/tasks
        │
        ▼
   任务写入 Redis ZSET (score=执行时间戳)
        │
        ▼  ──── Puller 主循环 ────
   batch_pop_due_tasks(now, limit=10)
        │
        ▼
   task_queue.put(task) × N
        │
        ▼  ──── Worker 主循环 ────
   task = await task_queue.get()
        │
        ▼
   await execute(task)  ← CrawlerEngine.execute()
        │
        ├─ 成功 → event_queue.put(SUCCESS)
        ├─ 失败 → event_queue.put(FAILURE)  with kind + reason + snapshot
        └─ 取消 → event_queue.put(CANCELLED)
        │
        ▼  ──── Monitor 主循环 ────
   await _drain_events()
        │
        ├─ SUCCESS  → 更新 task_history + WS 推送提交者
        ├─ FAILURE  → 写入 task_failures + 更新 task_history + WS 推送
        └─ CANCELLED→ 同 FAILURE 处理
```

## 1.4 全链路时序追踪

以管理员提交一个 `movie_crawl` 任务为例，穿越 6 层组件的完整时间线。

### Step 0 — `app.py` 启动：组件装配

```python
# app.py @before_serving → 一次性初始化所有基础设施

# 0a. 创建两个异步队列
app.task_queue  = asyncio.Queue(maxsize=45)       # 任务通道
app.worker_event_queue = asyncio.Queue(maxsize=1000)  # 事件通道

# 0b. 初始化 Crawler 单例（注入浏览器 + 事件队列）
init_crawler(browser=app.browser, ..., event_queue=app.worker_event_queue)
# crawler/__init__.py 中 create → _engine = CrawlerEngine(...)
# CrawlerEngine 内持有 ApiFetcher + BrowserFetcher

# 0c. init_puller(db_layer)      → Puller 单例  （持有 db_layer）
# 0d. init_browser_pool(...)     → BrowserPool 单例
#     └─ execute_func = crawler.execute  ← 从 crawler/__init__.py import
# 0e. init_monitor(...)          → Monitor 单例

# 0f. 启动 3 个后台协程
app.add_background_task(start_puller())        # Puller.run() 主循环
app.add_background_task(start_browser_pool())  # 创建 5 个 asyncio.Task → _worker_loop(i)
app.add_background_task(start_monitor())       # Monitor.run() 主循环
```

### Step 1 — 管理员 POST 提交任务

```
POST /admin/tasks
Authorization: Bearer <JWT>
Content-Type: application/json

{
    "type": "movie_crawl",
    "type_num": 11,
    "interval_id": "90:80"
}
```

```
          ┌─── 路由层 ───► routes/admin/task_routes.py ───► submit_task() ───┐
          │                                                                   │
          │  1. request.get_json() → body                                     │
          │  2. 校验 task_type ∈ {movie_crawl, review_crawl, ...}             │
          │  3. generate_id() → task_id (Snowflake)                           │
          │  4. 构造 task_data dict:                                          │
          │     { "id": 123456, "type": "movie_crawl",                        │
          │       "admin_id": g.user_id, "created_at": now,                   │
          │       "type_num": 11, "interval_id": "90:80" }                    │
          │                                                                   │
          └─── 5. task_json = json.dumps(task_data) ──────────────────────────┘
                                │
                                ▼
          ┌─── 注入层 ───► crawler/subtask.py ───► inject_subtask() ─────────┐
          │                                                                   │
          │  6. 调用 db.add_delayed_task_with_limit(                          │
          │       task_json=task_json,                                        │
          │       cooldown_seconds=2.0  ← 来自 puller_config)                 │
          │                                                                   │
          │  ┌───────── Redis Lua 原子执行 ─────────────────────────┐         │
          │  │ KEYS[1] = crawler:delay_queue                        │         │
          │  │ KEYS[2] = crawler:last_task_time                     │         │
          │  │                                                       │         │
          │  │ local last_time = GET(crawler:last_task_time)         │         │
          │  │ local execute_at = max(now, last_time + 2.0)          │         │
          │  │ SET(crawler:last_task_time, execute_at)               │         │
          │  │ ZADD crawler:delay_queue execute_at '{"id":123456,    │         │
          │  │       "type":"movie_crawl","admin_id":2906,...}'      │         │
          │  └───────────────────────────────────────────────────────┘         │
          │                                                                   │
          │  7. INSERT task_history (status='submitted')                      │
          │     └─ history 写入失败不影响主流程（任务已在 ZSET 中）              │
          │                                                                   │
          └─── 8. 返回 201 ───────────────────────────────────────────────────┘
                    {
                      "task_id": 123456,
                      "type": "movie_crawl",
                      "execute_at": 1717000123.456,
                      "message": "movie_crawl 任务已提交"
                    }
```

**关键点**：
- `execute_at = max(now, last_submit_time + 2s)` — 即使同一秒内提交 100 个任务，它们在 ZSET 中的 score 也至少差 2s
- history 写入与 ZADD **不在同一事务中** — 先 ZADD（保证任务必执行），后 INSERT history（失败只影响管理端可见性）
- 任务数据是 `json.dumps(dict)` 字符串存为 ZSET member，Puller 弹出后直接就是可执行的任务 JSON

### Step 2 — Puller 轮询 Redis → 放入 Queue

```
          ┌─── Puller.run() 主循环（每 ~0.1s~5s 迭代一次）───────────────────┐
          │                                                                   │
          │  9. 检查停止信号 STOPPED? → break                                 │
          │ 10. 检查队列饱和度:                                                │
          │     if qsize ≥ 45×0.8=36 → BACKPRESSURE → sleep 0.5s → continue   │
          │     if qsize ≤ 45×0.6=27 and in BACKPRESSURE → 恢复 RUNNING       │
          │                                                                   │
          │ 11. tasks = await db.batch_pop_due_tasks(now=time.time(), limit=10)│
          │                                                                   │
          │  ┌─────── Redis Lua 原子弹出 ───────────────────────────┐         │
          │  │ ZRANGEBYSCORE crawler:delay_queue -inf 1717000123.000 │         │
          │  │   LIMIT 0 10                                         │         │
          │  │ → 返回到期任务 JSON 列表                              │         │
          │  │ ZREM crawler:delay_queue "任务JSON1" "任务JSON2" ...  │         │
          │  └──────────────────────────────────────────────────────┘         │
          │                                                                   │
          │ 12. if tasks 为空:                                                │
          │       total_empty_polls += 1                                      │
          │       sleep = min(sleep × 1.5, 5.0)  ← 指数退避: 0.1→0.15→0.225...│
          │       continue                                                    │
          │                                                                   │
          │ 13. sleep 重置为 0.1s                                             │
          │ 14. for task in tasks:                                            │
          │       await task_queue.put(task)  ← 放入 asyncio.Queue            │
          │       total_fetched += 1                                          │
          └───────────────────────────────────────────────────────────────────┘
```

**关键点**：
- `batch_pop_due_tasks` 用 Lua 脚本保证 **ZRANGEBYSCORE + ZREM 原子性**。虽然当前单例部署不存在 Puller 竞态，但这是一种**防御性设计**——消除"查到后、删除前"的理论时间窗口，避免未来多实例部署时产生重复消费
- 默认单次拉 10 条 — 即使 Redis 有 100 条到期，也只取 10 条，剩余的留在 ZSET 中等待下一轮
- 指数退避：没任务时逐渐拉大轮询间隔（0.1 → 0.15 → 0.225 → ... → 5s），减少对 Redis 的空查压力

### Step 3 — Worker 从 Queue 取任务 → 执行

```
          ┌─── BrowserPool._worker_loop(worker_id=2) ────────────────────────┐
          │                                                                   │
          │ 15. if _shutting_down → break                                    │
          │                                                                   │
          │ 16. task = await task_queue.get()  ← 阻塞等待                     │
          │     └─ 取到: '{"id":123456,"type":"movie_crawl","type_num":11,...}'│
          │                                                                   │
          │ 17. 标记状态:                                                     │
          │     _worker_current_task[2] = task                                │
          │     _busy_counter += 1                                            │
          │     _busy_since[2] = now                                          │
          │                                                                   │
          │ 18. 上报 STARTED 事件:                                            │
          │     event_queue.put(WorkerEvent(STARTED, worker_id=2, task, ...)) │
          │                                                                   │
          │ 19. try: await self.execute(task)  ← 调用 crawler.execute(task) ──┤
          │         │                                                         │
          │         ▼ ┌─ CrawlerEngine.execute() ───────────────────┐         │
          │           │  data = json.loads(task)                     │         │
          │           │  task_type = "movie_crawl"                   │         │
          │           │  → _handle_movie_crawl(data)                 │         │
          │           └──────────────────────────────────────────────┘         │
          │                                                                   │
          │ 20. 成功: event_queue.put(WorkerEvent(SUCCESS, ...))              │
          │     失败: event_queue.put(WorkerEvent(FAILURE, kind=..., reason=..│
          │     取消: event_queue.put(WorkerEvent(CANCELLED, ...))            │
          │                                                                   │
          │ 21. finally:                                                      │
          │     _worker_current_task.pop(2)                                   │
          │     _busy_counter -= 1                                            │
          │     task_queue.task_done()        ← 通知 Queue 任务完成            │
          │                                                                   │
          │ 22. cooldown = random.uniform(120, 180) → sleep 157s             │
          │     └─ 期间不持任务、不计 busy → 回到 15                          │
          └───────────────────────────────────────────────────────────────────┘
```

**Worker-2 内部的 Crawler 子流程（movie_crawl）**：

```
CrawlerEngine._handle_movie_crawl(data)
│
├─ ① 确保 crawl_progress 行存在  → INSERT IGNORE
├─ ② 豆瓣 count API              → 获取 douban_total → UPDATE crawl_progress
├─ ③ 豆瓣 top_list API           → 获取 20 条 douban_id + title
│     └─ offset = ids_fetched（断点续爬）
│
├─ ④ 原子事务写入:
│     └─ INSERT IGNORE douban_ids (douban_id, title, source='dashboard_api', ...)
│     └─ UPDATE crawl_progress SET ids_fetched += 20
│     └─ 二者在同一事务中提交，保证断点续爬的 start 偏移正确
│
└─ ⑤ emit_stage 上报进度 → event_queue.put(STAGE_CHANGE)
```

**关键点**：
- `movie_crawl` 只负责 **补充 douban_id 库存**，不直接爬取详情页
- 详情页爬取由另一个任务类型 `movie_scrape_task` / `movie_detail_crawl` 负责
- `movie_crawl` 的事务写入保证：即使任务执行一半崩溃，`ids_fetched` 也不会错误推进

### Step 4 — 二级子任务链（movie_crawl 触发子任务）

```
movie_crawl
    │
    │  任务 JSON: {"type":"movie_crawl","type_num":11,"interval_id":"90:80"}
    │  → INSERT 20 条 douban_id 行 → 返回（任务本身结束）
    │
    ▼  不在 movie_crawl 内部，而是被另一套逻辑触发
    │
movie_detail_crawl  (独立任务, 某个管理员提交 或 自动触发)
    │
    │  BrowserFetcher → 详情页 HTML + 演职人员页 HTML
    │       success_callback → CrawlerEngine._inject_director_subtask()
    │       ├─ inject_subtask(task_type="director_crawl", ...)
    │       │  → ZADD crawler:delay_queue (带限速)
    │       │  → INSERT task_history (parent_task_id=父任务ID)
    │       │
    │       └─ inject_subtask(task_type="review_crawl", ...)
    │          → 同上
    │
    ▼
director_crawl  (子任务, Puller 拉取后执行)
    │
    │  BrowserFetcher → 演职人员页 HTML → parse_personnel() → save_crew()

```

```
任务家族树:

movie_crawl (parent)
  └─ movie_detail_crawl × N  (每个 douban_id 一个, parent_task_id=父任务)
       ├─ director_crawl (子任务, parent_task_id=movie_detail_crawl)
       └─ review_crawl    (子任务, parent_task_id=movie_detail_crawl)
              └─ review_body_crawl × M  (每条长评一个, parent_task_id=review_crawl)
```

每次子任务注入都通过 `inject_subtask()` 统一入口 → ZADD Redis + INSERT task_history → 回到 Step 1 的流程。

### 优雅关闭时 — 队列残留任务回写

```
app.after_serving():
  1. stop_puller()           → 不拉新任务
  2. stop_browser_pool()     → cancel 5 个 Worker, 等待 30s 超时
  3. Drain task_queue:
     while not task_queue.empty():
         task = task_queue.get_nowait()
         db.add_delayed_task(task, execute_at=now+5)  ← 写回 Redis ZSET
     → 重启后 Puller 从 Redis 恢复未执行的任务
  4. stop_monitor()
  5. close browser / DB pools
```

## 二、Puller — 延迟任务拉取器

**源码**: [background/puller.py](../background/puller.py)
**配置**: [config/puller_config.py](../config/puller_config.py)

### 2.1 职责

从 Redis ZSET（有序集合）中按 `score ≤ now` 批量弹出到期任务，放入 asyncio.Queue 供 Worker 消费。

### 2.2 状态机

```
          ┌─────────────┐
          │ INITIALIZED │  ← 构造后初始状态
          └──────┬──────┘
                 │ run()
          ┌──────▼──────┐    队列饱和(≥80%)   ┌──────────────┐
          │   RUNNING   │ ─────────────────→  │ BACKPRESSURE │
          └──────┬──────┘    队列恢复(≤60%)   └──────┬───────┘
                 │          ←─────────────────       │
                 │ stop()                     stop() │
          ┌──────▼──────────────────────────────────▼──┐
          │               STOPPED                       │
          └────────────────────────────────────────────┘
```

### 2.3 双阈值回滞机制（背压控制）

这是调度系统**最核心的流控设计**——防止任务队列爆满导致 OOM：

```python
# 进入背压: 队列饱和度 ≥ high_watermark (默认 80%)
# 退出背压: 队列饱和度 ≤ low_watermark  (默认 60%)
#
# 高水位和低水位之间的 [60%, 80%] 是回滞区（hysteresis）
# 作用: 避免在临界点反复进出背压（边界抖动）

high_watermark = queue_max * self.config.backpressure_high  # 0.8
low_watermark  = queue_max * self.config.backpressure_low   # 0.6
```

**为什么需要回滞区的对比演示**：

| 场景 | 单阈值 (只在 80%) | 双阈值 (80% 进 / 60% 出) |
|------|------------------|---------------------------|
| Worker 消化 1 个任务, 降至 79% | 立即恢复拉取 → 拉 1 个又到 80% → 又暂停 | 状态不变，继续处于背压 |
| Worker 连续消化到 70% | 持续在 79%~81% 来回切换 | 保持不变，稳定背压 |
| Worker 大量消化到 55% | 恢复到正常 | 退出背压，恢复拉取 |

### 2.4 指数退避休眠

无任务时休眠时间逐步增加，有任务时立即重置，减少 CPU 空转：

```
有任务领取 → sleep = base_sleep (0.1s)
无任务      → sleep = min(sleep × 1.5, max_sleep)
              sleep: 0.1s → 0.15s → 0.225s → 0.337s → ... → 5s (上限)
```

```python
# 拉到任务 → 立即重置
self._empty_wait = self.config.base_sleep

# 空轮询 → 指数增长，上限封顶
self._empty_wait = min(self._empty_wait * 1.5, self.config.max_sleep)
```

### 2.5 优雅关闭机制

```
调用 stop() → 设置 STOPPED 状态
                 │
    run() 下一次循环迭代时检测到 STOPPED → break 退出
                 │
    不调用 task.cancel()（让协程自然退出）
    不丢中间状态（当前迭代正常完成）
```

## 三、BrowserPool — 任务执行池

**源码**: [background/worker.py](../background/worker.py)

### 3.1 架构演进

从旧版 `WorkerPool`（动态伸缩 + 状态枚举）简化为 `BrowserPool`（固定容量 + 计数器）：

| 旧设计 (WorkerPool) | 新设计 (BrowserPool) | 变更原因 |
|---------------------|---------------------|---------|
| Worker 对象列表 + 独立状态枚举 | 无 Worker 对象，只有协程 Task | 简化状态管理，消除枚举不一致风险 |
| 动态 add/remove worker | 固定 `worker_count=5` | 浏览器内存预算固定，无需动态伸缩 |
| 浏览器资源由 Pool 持有 | 浏览器由 [BrowserFetcher](../crawler/fetcher.py) 内部管理 | 职责分离：调度器不持有 I/O 资源 |
| `WorkerState.IDLE/BUSY` 枚举 | `busy_count` 整数计数器 | asyncio 单线程保证原子性，无需枚举 |

### 3.2 固定容量协程池

```python
# 启动: 一次性创建 N 个 asyncio.Task
self._tasks = [
    asyncio.create_task(self._worker_loop(i), name=f"browser-worker-{i}")
    for i in range(worker_count)  # 默认 5
]

# 所有 Task 通过 asyncio.gather() 统一管理生命周期
await asyncio.gather(*self._tasks, return_exceptions=True)
```

### 3.3 Worker 主循环详解

### 3.4 反爬设计 — Worker 独立随机冷却

**设计精要**：冷却放在 Worker 层而非 Crawler 层，实现调度与业务分离。

```
时间轴 (5 Worker 并发):

Worker-0: ████████░░░░░░░░░░░░░░████████░░░░░░░░░░░░░░
Worker-1: ░░████████░░░░░░░░░░░░░░░░████████░░░░░░░░░░
Worker-2: ░░░░░░████████░░░░░░░░░░░░░░░░████████░░░░░░
Worker-3: ░░░░░░░░░░████████░░░░░░░░░░░░░░░░████████░░
Worker-4: ░░░░░░░░░░░░░░████████░░░░░░░░░░░░░░░░██████

████ = 执行任务 (busy)
░░░░ = 冷却休息 (cooldown, uniform(120, 180)s)

关键设计要点:
1. 每个 Worker 执行完后 uniform(120, 180) 随机休息 → 5 Worker 自然错峰
2. 休息期间不持有任务 → Puller 可以继续拉取新任务到队列
3. 休息期间不计 busy → 不影响队列饱和度判断和背压决策
4. 冷却放在 Worker 而非 Crawler — Worker 管调度节奏，Crawler 只管业务
```

**为什么是 120~180s？**
- 豆瓣的反爬策略通常基于**请求频率**检测，2~3 分钟的间隔模拟**真人阅读节奏**
- 5 个 Worker 各自独立随机，形成 24~36 秒的平均错峰间隔
- 接近真人"每半分钟看一部电影详情页"的行为模式

### 3.5 WorkerEvent 强类型合同

所有跨组件通信通过 Pydantic 模型校验，定义在 [crawler/failure_service.py](../crawler/failure_service.py)：

```python
class EventType(str, Enum):
    STARTED      = "started"       # 任务开始执行
    STAGE_CHANGE = "stage_change"  # Crawler 内部阶段变更
    SUCCESS      = "success"       # 任务执行成功
    FAILURE      = "failure"       # 任务执行失败
    CANCELLED    = "cancelled"     # 任务被取消

class FailureKind(str, Enum):
    NETWORK     = "network"       # DNS/代理/连接被拒
    TIMEOUT     = "timeout"       # 导航超时 / 读取超时
    HTTP        = "http"          # 4xx/5xx 状态码
    PARSE       = "parse"         # HTML/JSON 结构变化
    STORAGE     = "storage"       # MySQL/MongoDB 写入失败
    ABUSE       = "abuse"         # 豆瓣反爬
    VALIDATION  = "validation"    # 任务 JSON 非法
    BROWSER     = "browser"       # Chromium 进程崩溃
    UNKNOWN     = "unknown"       # 兜底

class WorkerEvent(BaseModel):
    event_type:  EventType
    worker_id:   int
    task:        str              # 原始任务 JSON
    timestamp:   float
    kind:        FailureKind = FailureKind.UNKNOWN
    reason:      str = ""
    stage:       str = ""         # STAGE_CHANGE 时的阶段描述
    snapshot:    Optional[dict] = None  # AI 失败时执行快照
    retry_count: int = 0
    max_retries: int = 0
```

### 3.6 异常分类策略

异常自动归类通过 `classify_exception()` 实现，优先级从高到低：

```
1. isinstance 精确匹配 → FetcherError
2. 类名字符串匹配  → PlaywrightTimeoutError, ValueError, DuplicateKeyError ...
3. 消息关键字兜底  → "abuse", "timeout", "404", "parse" ...
4. 最终兜底        → FailureKind.UNKNOWN
```

规则表（源码位置: [crawler/failure_service.py](../crawler/failure_service.py#L139-L197)）：

| 匹配方式 | 匹配内容 | 归类 |
|---------|---------|------|
| isinstance | `FetcherError` + "timeout" in msg | TIMEOUT |
| isinstance | `FetcherError` 其他 | NETWORK |
| 类名 | `ValueError`, `ValidationError` | VALIDATION |
| 类名 | `PlaywrightTimeoutError`, `TimeoutError`, `asyncio.TimeoutError` | TIMEOUT |
| 类名 | `ClientError`, `ServerError`, `HTTPError` | HTTP |
| 类名 | `DuplicateKeyError`, `IntegrityError`, `OperationalError` | STORAGE |
| 关键字 | "abuse", "检测到有异常请求" | ABUSE |
| 关键字 | "browser crashed", "target closed" | BROWSER |
| 关键字 | "timeout", "timed out", "超时" | TIMEOUT |
| 关键字 | "connection", "resolve", "refused" | NETWORK |
| 关键字 | "404", "not found" | HTTP |
| 关键字 | "parse", "解析" | PARSE |
| 其他 | 以上均不匹配 | UNKNOWN |

### 3.7 故障检测与自愈

三种故障形态：

| 形态 | 检测方式 | 自动恢复 | 原因 |
|------|---------|:---:|------|
| **死亡 (dead)** | `task.done() == True` | ✅ 自动重启 | `_worker_loop` 异常退出 |
| **卡死 (stuck)** | busy 时长 > `worker_timeout_alert`(300s) + 30s 余量 | ❌ 需人工介入 | `execute()` 永不返回，Task 仍在运行 |
| **崩溃 (crashed)** | 累计重启次数 | ✅ 自动重启 | 统计维度，非独立故障 |

**为什么卡死不能自动重启？**
> 卡死的 `asyncio.Task` 仍在运行，强行 `cancel()` 可能丢失正在执行的爬虫任务数据（已爬取但未入库的 HTML）。Monitor 只通过 WebSocket 告警，由管理员决策。

### 3.8 双重退出防线

```python
# 第一道防线: task.cancel() → CancelledError 传播到 await queue.get()
#              → 在 try/except asyncio.CancelledError 中 break

# 第二道防线: 检查 _shutting_down 标志
#             → 防止 cancel() 未能执行时（如异常路径）
#             → Worker 在下次循环迭代时主动检查并退出

if self._shutting_down:
    break
```

## 四、Monitor — 系统状态监视器

**源码**: [background/monitor.py](../background/monitor.py)
**配置**: [config/monitor_config.py](../config/monitor_config.py)

### 4.1 单轮监控流程

`_run_cycle()` 每 `interval` 秒（默认 10s）执行一轮：

```
  1. 采集 Puller 指标      → 状态/拉取数/空轮询/背压次数+时长
  2. 采集队列指标          → qsize / maxsize / saturation
  3. 采集 BrowserPool 指标 → idle/busy/cooldown/alive/dead/stuck
     ├─ 处理死 Worker       → 标记任务失败 + 自动重启 + WS 告警
     └─ 处理卡 Worker       → WS 告警（不自动重启）
  4. 消费 Worker 事件队列  → SUCCESS 计数 / FAILURE 写库 / CANCELLED 写库
  5. 采集系统资源          → CPU% / 内存%
  6. 数据库健康检查        → MySQL / Redis / MongoDB ping
  6b. Cookie 状态检查      → 活跃账号数 / dbcl2 有效性
  7. 输出报告 + WS 广播    → 安全字段白名单过滤后推送全体管理员
```

**容错设计**：单轮内任何步骤异常不影响后续步骤和下一轮。

```python
async def _run_cycle(self):
    report = {}
    
    # 每个步骤独立 try/except，互不阻塞
    try:
        report["puller_state"] = puller.state
        # ...
    except Exception as e:
        report["puller_error"] = str(e)  # 记录错误，继续下一步
    
    try:
        report["queue_size"] = self.task_queue.qsize()
        # ...
    except Exception as e:
        report["queue_error"] = str(e)
    # ...
```

### 4.2 WorkerEvent 消费管道

```
event_queue
    │
    ▼
WorkerEvent.model_validate(raw)  ← Pydantic 强类型校验
    │
    ├─ 校验通过 → 按 event_type 分发
    └─ 校验失败 → 丢弃 + WARNING 日志
```

5 种事件类型的处理详情：

| EventType | Monitor 处理 | 副作用 |
|-----------|-------------|--------|
| `STARTED` | 更新 task_history → `running` + WS 推送提交者 | MySQL UPDATE |
| `STAGE_CHANGE` | 更新 task_history.message + WS 推送进度 | MySQL UPDATE |
| `SUCCESS` | 全局计数 + 更新 task_history → `done` + WS 推送 | MySQL UPDATE |
| `FAILURE` | 全局计数 + 写入 `task_failures` 表 + 更新 task_history + WS 推送 | MySQL INSERT + UPDATE |
| `CANCELLED` | 全局计数 + 同 FAILURE 处理 | MySQL INSERT + UPDATE |

**单轮消费上限**：`max_events_per_cycle`（默认 500），防止事件积压时 Monitor 自身阻塞过久。

## 六、生命周期管理

### 6.1 启动流程

```
app.before_serving() 阶段:
    
    1. 创建两个 asyncio.Queue
       task_queue  = asyncio.Queue(maxsize=N)
       event_queue = asyncio.Queue()

    2. 初始化单例
       init_puller(task_queue, db_layer)
       init_browser_pool(task_queue, execute_func, event_queue, worker_count=5)
       init_monitor(task_queue, event_queue, db_layer, ws_manager=ws)

    3. 注册后台任务（作为 asyncio.Task 启动）
       app.add_background_task(start_puller())       # Puller.run()
       app.add_background_task(start_browser_pool())  # BrowserPool.start() → gather 5 Worker
       app.add_background_task(start_monitor())       # Monitor.run()
```

### 6.2 关闭流程

```
app.after_serving() 阶段:
    
    1. stop_puller()         → 设置 STOPPED → run() 下次迭代检测后退出
    2. stop_browser_pool()   → task.cancel() × 5 → 等待 30s 超时 → 强制继续
    3. stop_monitor()        → 设置 STOPPED → run() 下次迭代检测后退出
```

### 6.3 关闭顺序考量

```
推荐顺序: Puller → BrowserPool → Monitor

原因:
  1. 先停 Puller    → 不再有新任务入队
  2. 再停 Worker    → 等待当前正在执行的任务完成（30s 超时保护）
  3. 最后停 Monitor → 确保最后的事件被消费完毕，不丢失败记录
```

## 七、Redis 键空间设计

调度系统重度依赖 Redis，所有键遵循 `{namespace}:{entity}` 命名规范，统一通过 `RedisConfig` 管理前缀。

### 7.1 键全景表

| Key | 类型 | 配置来源 | 写入方 | 读取方 | 说明 |
|-----|------|---------|--------|--------|------|
| `crawler:delay_queue` | **ZSET** | `RedisConfig.delay_queue_key` | 管理员提交 / subtask | Puller | 延迟任务队列，`score=执行时间戳`, `member=任务JSON` |
| `crawler:last_task_time` | **String** | `RedisConfig.rate_limit_key` | `add_delayed_task_with_limit()` | 同一个 Lua 脚本 | 上次提交时间戳，用于限速冷却（`score = max(now, last + 2s)`） |
| `crawler:dedup:review_body:{review_id}` | **String** | 硬编码 | `POST /admin/tasks` | `POST /admin/tasks` | review_body_crawl 去重标记，TTL=3600s（1小时），覆盖任务生命周期 |
| `monitor:storage_failures` | **ZSET** | 硬编码 | Monitor._check_storage_failure | Monitor._get_storage_failure_count | Storage 失败滑动窗口，`score=timestamp`, ZREMRANGEBYSCORE 自动清理 5min 前数据，TTL=600s |
| `monitor:storage_alert_cooldown` | **String** | 硬编码 | Monitor._check_storage_failure | Monitor._check_storage_failure | Storage 告警冷却标记，TTL=120s，存在时跳过告警 |
| `wordcloud:movie:{movie_id}` | **String** | 硬编码 | Crawler._handle_ai_wordcloud | `GET /user/movies/<id>/comment-wordcloud` | AI 词云缓存，JSON 格式 `{words, total_words, updated_at}` |
| `ratelimit:{endpoint}:{identifier}` | **String** | `utils/rate_limit.py` 硬编码 | `check_rate_limit()` | `check_rate_limit()` | 请求频率计数器，INCR + 首次 EXPIRE，如 `ratelimit:login:192.168.1.1` |
| `ratelimit:events:{endpoint}` | **ZSET** | `utils/rate_limit.py` 硬编码 | `check_rate_limit()` | 审计日志查询 | 超限事件审计记录，TTL=86400s（24h） |

### 7.2 核心键详解

#### 7.2.1 `crawler:delay_queue` — 延迟任务队列（ZSET）

```redis
ZADD crawler:delay_queue 1717000000.123 '{"type":"movie_detail_crawl","douban_id":"1292052",...}'
ZADD crawler:delay_queue 1717000002.456 '{"type":"review_crawl","douban_id":"1292052",...}'
```

**核心操作 — 原子批量弹出到期任务（Lua 脚本）**：

```lua
-- LUA_BATCH_POP: ZRANGEBYSCORE + ZREM 原子执行
local members = redis.call('ZRANGEBYSCORE', key, '-inf', now, 'LIMIT', 0, limit)
if #members > 0 then
    redis.call('ZREM', key, unpack(members))
end
return members
```

**为什么用 Lua 脚本？**
- 消去 ZRANGEBYSCORE 与 ZREM 之间的理论时间窗口——当前单例 asyncio 已天然串行，Lua 是**防御性设计**，预留未来多实例部署时的原子性保障

#### 7.2.2 带限速的写入（Lua 脚本）

```lua
-- LUA_ADD_WITH_RATE_LIMIT: 保证相邻任务 score 至少间隔 cooldown 秒
local last_time = redis.call('GET', KEYS[2])  -- crawler:last_task_time
local execute_at = now

if last_time then
    local next_available = tonumber(last_time) + cooldown
    if next_available > now then
        execute_at = next_available  -- 推到未来
    end
end

redis.call('SET', KEYS[2], execute_at)
redis.call('ZADD', KEYS[1], execute_at, task_json)
return execute_at
```

**效果演示**：

```
提交时间线 (cooldown=2s):
  任务A: now=10:00:00.000 → execute_at=10:00:00.000
  任务B: now=10:00:00.300 → execute_at=10:00:02.000  ← 被推到 +2s
  任务C: now=10:00:00.600 → execute_at=10:00:04.000  ← 被推到 +4s
  任务D: now=10:00:03.000 → execute_at=10:00:04.000  ← 自然错开

→ ZSET 内相邻 score 至少差 2s
→ Puller 按 score 到期拉取，自然间隔 ≥ 2s
```

#### 7.2.3 `monitor:storage_failures` — Storage 失败滑动窗口（ZSET）

```
ZADD monitor:storage_failures 1717000100 '{"reason":"...","db_failed":["mysql"],"ts":1717000100}'
ZREMRANGEBYSCORE monitor:storage_failures -inf 1716999800  ← 清理 5 分钟前
ZCOUNT monitor:storage_failures 1716999800 1717000100     ← 窗口内计数
```

**告警策略**：5 分钟内 ≥ 3 次 → ERROR 日志 + WS 全体广播，随后 120s 冷却期不重复告警。

#### 7.2.4 `crawler:dedup:review_body:{review_id}` — 长评正文去重

```
SET crawler:dedup:review_body:12345678 "1" EX 3600
```

- **写入时机**：管理员提交 `review_body_crawl` 任务时
- **清除时机**：任务成功/失败后，由 Monitor 主动 `DEL`，释放被阻塞的重提交
- **TTL 兜底**：即使 Monitor 漏清，1 小时后自动过期

### 7.3 键命名规范

```
{namespace}:{entity}[:{sub_entity}]

namespace:
  crawler:  爬虫相关（延迟队列、去重、限速）
  monitor:  监控告警（storage 失败计数、冷却期）
  wordcloud:  AI 生成缓存（词云数据）
  ratelimit: API 限流（登录频率、审计事件）
```

### 7.4 配置驱动 vs 硬编码

| 键 | 可配置 | 可配置原因 |
|----|:---:|-----------|
| `crawler:delay_queue` | ✅ `.env` → `REDIS_DELAY_QUEUE_KEY` | 多环境可能需要不同实例的队列隔离 |
| `crawler:last_task_time` | ✅ `.env` → `REDIS_RATE_LIMIT_KEY` | 同上 |
| `crawler:dedup:review_body:{id}` | ❌ 硬编码 | 单一功能，无需隔离 |
| `monitor:storage_failures` | ❌ 硬编码 | Monitor 内部自用 |
| `monitor:storage_alert_cooldown` | ❌ 硬编码 | Monitor 内部自用 |
| `wordcloud:movie:{id}` | ❌ 硬编码 | 单一缓存用途 |
| `ratelimit:{endpoint}:{id}` | ❌ 硬编码 | 限流逻辑不变 |

## 八、反爬流控全景

调度系统与爬虫引擎的流控策略形成四层防御体系（详见 [反爬与流控策略.md](反爬与流控策略.md)）：

| 层级 | 位置 | 机制 | 调度系统关联 |
|------|------|------|-------------|
| Layer 1: 提交冷却 | `subtask.py` | ZSET score 最小间隔 2s | Puller 按 score 拉取，自然错峰 |
| Layer 2: Puller 节流 | `puller.py` | 双阈值背压 + 指数退避 | **核心实现在调度系统** |
| Layer 3: 并发控制 | `crawler/__init__.py` | Browser Semaphore | 限制同时打开的浏览器页面数 |
| Layer 4: Worker 休眠 | `worker.py` | 执行后随机 sleep 120~180s | **核心实现在调度系统** |

## 九、设计审查

### 9.1 架构优点

| # | 设计亮点 | 说明 |
|---|---------|------|
| 1 | **三组件 Queue 解耦** | Puller / Worker / Monitor 通过两个 asyncio.Queue 完全隔离，各自可独立测试和替换 |
| 2 | **双阈值回滞** | 背压控制避免边界抖动，是经典的控制论设计模式 |
| 3 | **WorkerEvent 强类型合同** | Pydantic 校验确保跨组件通信的类型安全，非法事件直接丢弃 |
| 4 | **降级路径** | Storage 失败计数 Redis 不可用时降级到内存，不丢失监控能力 |
| 5 | **双重退出防线** | `CancelledError` + `_shutting_down` 标志位，防止优雅关闭失败 |
| 6 | **WS 推送白名单** | 广播前过滤敏感字段，防止密码/Token 泄露到前端 |
| 7 | **依赖注入 + 单例管理** | 构造函数注入外部依赖 + 模块级单例 getter，可测试、可替换 |
| 8 | **Worker 冷却独立错峰** | 5 个 Worker 各自独立 `uniform(120, 180)` 休息，自然形成反爬间隔 |
| 9 | **Monitor 单步容错** | 每轮 8 个步骤各自独立 try/except，任一步骤失败不影响其他步骤 |
| 10 | **pydantic-settings 全配置化** | 所有调优参数可通过 `.env` 覆盖，无需改代码即可适配不同环境 |

### 9.2 潜在风险与改进建议

| # | 问题 | 风险等级 | 改进建议 |
|---|------|:---:|---------|
| 1 | `_busy_counter` 依赖 asyncio 单线程保证原子性 | 低 | 当前安全。若未来引入 `run_in_executor`，需加 `asyncio.Lock` 或文档注明 |
| 2 | `cooldown_count` 属性遍历 `_cooldown_until` 字典 | 低 | n=5 时 O(n) 可忽略，若扩到 100+ 需改用整数计数器 |
| 3 | 卡死检测阈值 `330s` 硬编码 | 中 | 应改为 `self.config.worker_timeout_alert + 30`，随环境变量可调 |
| 4 | `_storage_failures_fallback` 内存列表无自动清理 | 中 | 长期 Redis 不可用时内存持续增长，建议加 maxsize 限制或定时清理 |
| 5 | Monitor `_drain_events()` 单轮最多消费 500 事件 | 低 | 当前 10s × 500 = 50 events/s 吞吐足够，高峰期需关注 |
| 6 | Puller 每轮只拉 batch_size=10 条 | 低 | 配合 task_cooldown 2s，日常足够。大促时可通过环境变量提高 |
