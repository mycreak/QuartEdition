# 短评词云功能 前后端协调文档
> 最后更新：2026-05-14
> 状态：待后端开发
> 功能目标：在电影详情页新增短评词云模块，提取该电影所有短评的高频关键词可视化展示，帮助用户快速了解观众评价侧重点

***

## 一、功能概述
### 核心需求
1. 展示位置：电影详情页，短评列表上方/单独Tab栏展示
2. 功能说明：将某部电影的所有短评进行分词统计，提取高频关键词，以词云形式展示，关键词权重越高，字体越大
3. 可选交互：点击词云中的关键词，可筛选短评列表，仅展示包含该关键词的短评

### 用户操作流程
```
用户进入电影详情页 → 前端请求该电影的词云数据 → 后端返回关键词列表 → 前端渲染词云
→ （可选）用户点击关键词 → 短评列表自动筛选，仅展示包含该关键词的短评
```

***

## 二、前端实现方案
### 前端依赖能力
1. 词云渲染组件选型：采用成熟开源方案 `echarts-wordcloud` 或 `vue-wordcloud`，支持自定义大小、颜色、点击事件
2. UI交互：
   - 加载状态：词云加载中展示骨架屏
   - 空状态：电影没有短评时展示「暂无足够短评生成词云」提示
   - （可选）hover关键词展示出现次数/短评预览
   - （可选）点击关键词筛选短评列表，高亮关键词

### 前端需要的接口数据
仅需要后端提供词云基础数据，前端负责渲染即可，无额外复杂计算。

***

## 三、后端需求&接口定义
### 1. 需要提供的接口
#### 接口名称：获取电影短评词云数据
`GET /movies/{movie_id}/comment-wordcloud`
> 权限：和电影详情页一致，普通登录用户可访问

#### 请求参数
| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| movie_id | number | ✅ | 电影ID（本地数据库电影ID） |

#### 返回结构
```json
{
  "success": true,
  "data": {
    "words": [
      {
        "text": "剧情紧凑", // 关键词文本
        "weight": 120, // 权重（值越大，词云展示字体越大）
        "color": "#f44336" // （可选）词的颜色，前端也可自动生成
      },
      {
        "text": "演技在线",
        "weight": 98,
        "color": "#2196f3"
      }
    ],
    "total_words": 120, // 总有效关键词数量
    "updated_at": "2026-05-13T12:00:00Z" // 词云数据最后更新时间
  }
}
```

### 2. 后端需要实现的核心逻辑
#### 基础能力
1. **分词&关键词提取**：对电影的所有短评进行分词，过滤停用词（如"的、了、啊"等无意义助词）、敏感词，提取有效关键词
2. **词频统计**：统计每个关键词的出现次数，计算权重（权重越大，字体越大）
3. **缓存优化**：词云数据不需要实时更新，建议缓存1-24小时（根据短评更新频率调整），避免每次请求都重新计算，减少性能消耗
4. **更新触发**：建议在每次爬取新的短评后，异步重新计算该电影的词云数据，不需要实时响应

#### 可选优化
1. 关键词去重：合并相近含义的词（如"好看"和"超好看"可以合并，或者保留权重高的）
2. 情感配色：根据关键词的正负向情感，给不同的颜色（好评偏绿色，差评偏红色）

***

## 四、待确认的疑问点
### 🎯 需要和后端对齐的核心问题
1. **分词&关键词提取方案**：后端用什么算法/库实现？是用jieba分词提取普通关键词，还是用大模型提取评价类总结词？返回的关键词是单个词、词组还是短句？
2. **权重计算规则**：权重是按关键词出现的绝对值次数，还是按出现频率（次数/总短评数）？需要对齐，保证前端展示的字体大小梯度合理。
3. **数据更新时机**：词云数据多久更新一次？是每次新增短评就更新，还是定时任务批量更新？
4. **权限控制**：该接口的访问权限是否和电影详情页保持一致？（不需要额外权限，登录用户可访问）
5. **颜色规则**：关键词的颜色是后端返回，还是前端自动生成？如果前端生成的话，接口不需要返回`color`字段。
6. **点击筛选功能是否需要后端支持**：如果要实现点击关键词筛选短评的功能，是前端根据短评内容自行过滤，还是需要后端提供按关键词搜索短评的接口？
7. **数据量级限制**：最多返回多少个关键词？建议返回前50-100个高频词即可，过多会导致词云拥挤看不清。

## 七、后端结论与回应（2026-05-14）

### 7.1 对齐决策一览

| # | 前端疑问 | 后端结论 |
|---|---------|---------|
| 1 | 分词方案？jieba 还是大模型？ | **DeepSeek 大模型**，提取评价类关键词（词组级别），不引入 jieba |
| 2 | 权重按词频还是比例？ | **AI 自动评估重要性**，范围 0-200，非纯词频 |
| 3 | 多久更新一次？ | **Redis 缓存 24h + 按需生成**，非定时任务 |
| 4 | 权限？ | **`require_login`**，和电影详情页一致 |
| 5 | 颜色谁出？ | **前端自动生成**，接口不返回 `color` 字段 |
| 6 | 点击筛选要后端接口吗？ | **不需要**，前端 filter 现有短评列表数据 |
| 7 | 最多多少关键词？ | **30-50 个** |

### 7.2 各决策的详细理由

#### 1. 分词方案：DeepSeek 大模型

- jieba 未安装，需要额外依赖，增加部署复杂度
- DeepSeek 已在项目中成熟使用（`utils/ai_client.py`），无额外接入成本
- 大模型输出的"评价类关键词"更符合词云语义场景（例：「演技炸裂」不会被机械拆成「演技」+「炸裂」）
- 输出格式直接对齐前端：`[{text: "演技炸裂", weight: 150}, ...]`

#### 2. 权重：AI 评估而非纯词频

- 纯词频会导致「电影」「不错」「还行」等高频无意义词占据最高权重
- 大模型可根据上下文语义判断哪些词真正代表观众评价侧重点
- 权重范围 0-200，前端直接映射字体大小

#### 3. 更新时机：Redis 缓存 24h

```
请求 GET /movies/{movie_id}/comment-wordcloud
  ├─ Redis 命中 → 直接返回（~1ms）
  └─ Redis 未命中
      ├─ MongoDB 取该电影所有短评文本
      ├─ 短评数 < 10 → 返回空（不调 AI）
      └─ 短评数 >= 10 → DeepSeek 生成 → Redis SETEX 24h → 返回
```

#### 4. 权限：登录即可

无需额外管理权限，`require_login` 和电影详情页完全一致。

#### 5. 颜色：前端自动生成

echart-wordcloud 组件自带多种配色方案（`color: ['#f44336', '#2196f3', ...]`），前端直接配置即可，接口不冗余返回。

#### 6. 点击筛选：前端自过滤

短评列表接口 `GET /user/reviews?movie_id=N` 已返回完整短评内容，前端通过 `Array.filter(text.includes(keyword))` 即可实现，不需要后端提供关键词搜索接口。

#### 7. 关键词数量：30-50 个

- < 30 个：词云过稀，视觉空荡
- > 50 个：词云拥挤，辨识度下降
- 短评不足 10 条时返回空数组，前端展示「暂无足够短评生成词云」

### 7.3 最终接口定义

```
GET /user/movies/<movie_id>/comment-wordcloud
Content-Type: application/json
Authorization: Bearer <token>
```

**成功响应**：
```json
{
  "success": true,
  "data": {
    "words": [
      { "text": "演技炸裂", "weight": 150 },
      { "text": "剧情拖沓", "weight": 120 },
      { "text": "画面精美", "weight": 95 }
    ],
    "total_words": 45,
    "updated_at": "2026-05-14T12:00:00Z"
  }
}
```

**空数据响应**（短评不足 10 条）：
```json
{
  "success": true,
  "data": {
    "words": [],
    "total_words": 0,
    "updated_at": null
  }
}
```

**错误响应**（AI 调用失败）：
```json
{
  "success": false,
  "error": "词云生成失败，请稍后重试"
}
```
HTTP 500
