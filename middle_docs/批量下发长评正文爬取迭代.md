# 批量下发长评正文爬取 — 前后端协调文档

> 最后更新：2026-05-13

---

## 一、需求概述

管理员可以在后台**一键多选**某部电影的所有待爬长评正文，批量提交为多个独立的 `review_body_crawl` 单条任务。

---

## 二、整体流程

```
┌──────────────────────────────────────────────────────────────────┐
│ 管理员操作流程                                                     │
│                                                                   │
│  ① 选择任务类型: [爬取长评正文 ▾]                                    │
│                                                                   │
│  ② 选择电影: [《将来的事》 ▾]                                       │
│     ↑ 接口 A: GET /admin/movies/with-pending-reviews               │
│                                                                   │
│  ③ 勾选长评（每页10条，支持全选本页）:                                │
│     ☑ 影评1: "我只想记录下她在..." (有用: 168)                     │
│     ☑ 影评2: "于佩尔的表演如同..." (有用: 120)                     │
│     ☐ 影评3: "法国文艺片的标杆..." (有用: 95)                      │
│     ↑ 接口 B: GET /admin/movies/{movie_id}/pending-reviews          │
│                                                                   │
│  ④ 确认提交                                                        │
│     → 前端循环 POST /admin/tasks × N 次                            │
│     → 每条独立成单任务，ZSET score 由 task_cooldown=2s 自动错开     │
└──────────────────────────────────────────────────────────────────┘
```

## 三、后端接口

### 接口 A：有 pending 长评的电影列表

```
GET /admin/movies/with-pending-reviews

认证: Bearer JWT（管理员）
响应 200:
{
  "items": [
    {"movie_id": 21, "title": "将来的事 L'avenir", "pending_count": 47},
    {"movie_id": 35, "title": "肖申克的救赎",             "pending_count": 12}
  ]
}
```

**SQL**：
```sql
SELECT m.id AS movie_id, m.title,
       COUNT(mr.review_id) AS pending_count
FROM movies m
JOIN movie_review mr ON m.id = mr.movie_id
WHERE mr.status = 'pending'
GROUP BY m.id, m.title
ORDER BY pending_count DESC
```

**实现位置**：`routes/admin/movie_routes.py`（新增）

```
GET /admin/movies/{movie_id}/pending-reviews?page=1&page_size=10
```

```sql
ORDER BY useful_count DESC
LIMIT %s OFFSET %s
```

### 接口 C：提交任务（增强去重逻辑）

在现有 `POST /admin/tasks` 中新增针对 `review_body_crawl` 的去重校验：

```
POST /admin/tasks
Body: {
  "type": "review_body_crawl",
  "douban_id": "26215216",
  "review_id": "8180317",
  "title": "我只想记录下她在母亲葬礼读的那段话",
  "author": "ev***"
}

去重逻辑：
  ① SELECT status FROM movie_review WHERE review_id = ?
     - status='done' → 已爬取成功，直接返回 "已忽略（已爬取成功）"
     - status='failed' → 允许重新提交（重试）
  
  ② 查询 Redis ZSET 是否已有该 review_id
     - 已在队列 → 返回 "已忽略（已在待执行队列中）"

正常响应 201:
{"task_id": 123456, "type": "review_body_crawl", "message": "任务已提交"}

重复响应 200:
{"skipped": true, "reason": "已爬取成功|已在待执行队列中"}
```

**前端循环提交时的体验提升**：

```javascript
// 前端伪代码
let submitted = 0, skipped = 0
const skipReasons = []

for (const item of selectedItems) {
  const resp = await fetch('/admin/tasks', {
    method: 'POST',
    body: JSON.stringify({
      type: 'review_body_crawl',
      douban_id: movieDoubanId,
      review_id: item.review_id,
      title: item.title,
      author: item.author
    })
  })
  const data = await resp.json()
  if (data.skipped) {
    skipped++
    skipReasons.push(`${item.review_id}: ${data.reason}`)
  } else {
    submitted++
  }
}

// 反馈示例:
alert(`成功提交 ${submitted} 条，${skipped} 条重复已忽略`)
// 详情: 8180317: 已爬取成功 / 8182345: 已在待执行队列中
```

**实现位置**：在 `routes/admin/task_routes.py` 的 `submit_task()` 中 `review_body_crawl` 分支新增去重查询。

## 四、前端交互

| 步骤 | 交互元素 | 说明 |
|------|---------|------|
| 选择任务类型 | 下拉栏 | 选 `review_body_crawl`（爬取长评正文） |
| 选择电影 | 下拉栏 | 调用接口 A 获取有 pending 长评的电影列表 |
| 勾选长评 | 表格 + 复选框 | 调用接口 B 获取列表，分页 10 条，支持全选本页 |
| 提交 | 按钮 | 循环 POST，显示进度（已提交 X/N），失败项收集并提示 |

**全选与循环提交无需前端 sleep**——`task_cooldown=2s` 在前端循环提交时通过 ZSET 自然间隔即可，Worker 侧的 `worker_rest=120~300s` 会在执行时自然错峰。

---

## 五、任务分发与反爬协调

```
前端循环提交
  ↓ 每次 POST
后端 POST /admin/tasks
  → task_data = {type: "review_body_crawl", review_id, ...}
  → zadd ZSET score = max(now, last + 2s)    ← task_cooldown 错开入队
  ↓
Puller 拉取到期任务 → asyncio.Queue
  ↓
Worker 取任务 → execute(单条爬取, ~25s) → busy--
  ↓
Worker rest 120~300s（不计 busy）→ 再取下一个              ← worker_rest 错开执行
```

| 层级 | 机制 | 作用 |
|------|------|------|
| 提交层 | `task_cooldown=2s` | ZSET score 错开，防止一瞬间全部入队 |
| 队列层 | Puller 背压 | Queue 满时暂停拉取 |
| 执行层 | `worker_rest=120~300s` | 每条间隔 2~5 分钟，反爬核心防线 |

## 六、权限控制

3 个接口（接口 A / B / C）直接复用现有 `crawler:task:write` 权限，无需新增权限点：

| 接口 | 权限 | 说明 |
|------|------|------|
| `GET /admin/movies/with-pending-reviews` | `crawler:task:write` | 复用 |
| `GET /admin/movies/{movie_id}/pending-reviews` | `crawler:task:write` | 复用 |
| `POST /admin/tasks`（已有） | `crawler:task:write` | 无需改动 |

## 七、接口兼容性

原来的单条 `review_body_crawl` 提交入口**保留不动**，与新批量入口并行：

| 场景 | 入口 | 适用 |
|------|------|------|
| 批量提交 | 新交互：下拉选电影 → 勾选列表 → 批量 POST | 管理员一次性处理某部电影的所有 pending 长评 |
| 单条提交 | 旧交互：手动输入 review_id / douban_id / title 等 | 测试、补漏、非标准场景 |
| 自动提交 | `review_crawl` 内部自动 inject | 爬虫流程中自动触发 |

三种方式共享同一个 `POST /admin/tasks` + `review_body_crawl` 任务类型，互不干扰。

## 八、前端改动量

改动范围仅限于 **替换表单输入** → **新选择交互**：

| 组件 | 改动 |
|------|------|
| 任务类型下拉 | 无需改动（`review_body_crawl` 已存在） |
| 参数输入区 | **替换**：手动输入框 → 下拉选电影 + 表格勾选 |
| 提交按钮 | **逻辑增强**：循环 POST + 收集结果反馈 |
| 任务列表 | 无需改动（复用现有任务历史展示） |
| 进度展示 | 无需改动（复用现有 Puller/Worker 状态） |
| 权限校验 | 无需改动（复用 `crawler:task:write`） |

## 九、设计决策

| 决策 | 原因 |
|------|------|
| **不做新的批量任务类型** | 前端循环 POST 即可，后端零新增逻辑 |
| **movie_id 可选** | 已支持——未传时后端用 `douban_id` 查询 |
| **失败隔离** | 某条失败不影响其他条，各自独立 retry |
| **前端容错** | 循环中某次 POST 失败不中断，收集失败列表通知用户 |
| **无批量删除/取消** | 单条任务的优点就是低耦合，不需要批量回滚 |
