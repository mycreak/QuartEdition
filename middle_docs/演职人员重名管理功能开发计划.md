# 演职人员重名管理功能开发计划
## 一、功能概述
### 解决问题
解决管理员手动录入无豆瓣ID的演职人员时，可能出现的同名人员重复入库问题，支持管理员人工校验合并，保证数据准确性。
### 核心流程
1. **录入阶段**：管理员手动新增无豆瓣ID的演职人员时自动检测重名，标记待处理
2. **处理阶段**：管理员在重名管理列表中判断同名人是否为同一人，支持合并或确认不是同一人
3. **数据隔离**：合并后的无效人员自动从所有业务场景中过滤，不影响现有功能

### 🎯 阶段一：数据库层改造（优先级P0，依赖无，预计开发0.5天）
#### 子任务
| 任务内容 | 说明 | 校验标准 |
|----------|------|----------|
| 1. `people`表新增字段 | 已完成：`admin_id`（录入管理员ID，默认0）、`is_duplicate`（重名标记，默认0） | 执行升级SQL后字段存在，默认值正确 |
| 2. 新建`duplicate_name`重名表 | 建表语句见下方，加唯一约束避免重复记录 | 表创建成功，唯一约束生效 |
| 3. 新增索引优化 | 给`people.name`加普通索引，`duplicate_name(person_id1, person_id2)`加唯一索引 | 查询重名SQL走索引，毫秒级返回 |
#### 相关SQL
```sql
-- 新增字段（已写入文档，直接执行即可）
ALTER TABLE people ADD COLUMN admin_id INT NOT NULL DEFAULT 0 COMMENT '录入的管理员ID，0代表爬虫自动录入' AFTER douban_id;
ALTER TABLE people ADD COLUMN is_duplicate TINYINT NOT NULL DEFAULT 0 COMMENT '重名标记：0=无重名/已确认，1=待确认重名，-1=无效重复记录' AFTER admin_id;
CREATE INDEX idx_people_name ON people(name);
-- 新建重名表
CREATE TABLE IF NOT EXISTS duplicate_name (
  id              INT AUTO_INCREMENT PRIMARY KEY,
  name            VARCHAR(128) NOT NULL COMMENT '重名姓名',
  person_id1      INT NOT NULL COMMENT '重名人员ID1（保证person_id1 < person_id2）',
  person_id2      INT NOT NULL COMMENT '重名人员ID2',
  is_checked      TINYINT NOT NULL DEFAULT 0 COMMENT '0待处理 1已处理',
  created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  checked_at      DATETIME NULL COMMENT '处理时间',
  operate_admin_id INT NULL COMMENT '处理的管理员ID',
  UNIQUE KEY uk_pair(person_id1, person_id2) COMMENT '唯一约束，避免同一对重名重复写入'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 🎯 阶段二：后端接口开发（优先级P0，依赖阶段一完成，预计开发2天）
#### 2.1 第一部分：现有接口适配重名检测（预计0.5天）
| 接口/方法 | 修改内容 | 校验标准 |
|----------|----------|----------|
| 1. 新增管理员手动加人专用接口 `POST /admin/movie/{movie_id}/add_credit_manual` | 入参：`name`（必填）、`douban_id`（可选）、`role_type`（必填）、`admin_id`（当前登录用户）<br>逻辑：<br>1. 有`douban_id`时优先匹配ID，存在直接关联，不存在新增人员<br>2. 无`douban_id`时检测同名人：<br>   - 无重名：直接新增人员，`is_duplicate=0`，`admin_id`填当前用户，然后关联电影<br>   - 有重名：开启事务，新增人员后，将所有匹配的同名人（含新人员）`is_duplicate=1`，两两成对写入`duplicate_name`表，最后关联电影 | 手动新增无ID的重名人员时，`duplicate_name`自动生成记录，`people.is_duplicate`正确标记为1 |
| 2. 现有`add_credit`接口兼容 | 无修改，仅新增手动录入专用接口，不影响爬虫逻辑 | 原有爬虫、手动选已有人员的关联逻辑完全正常 |
#### 2.2 第二部分：重名管理接口（预计1.5天）
所有接口需要`movie:manage`权限
| 接口 | 方法 | 入参 | 返回值 | 说明 |
|------|------|------|--------|------|
| `/admin/duplicate_person/list` | GET | `page`、`page_size` | `{items: [{id, name, person_id1, person_name1, person_id2, person_name2, created_at}], total}` | 重名待处理列表，仅返回`is_checked=0`的记录 |
| `/admin/duplicate_person/{person_id}/movies` | GET | `person_id` | `[{movie_id, title, poster, year, regions: [], role_type}]` | 人员关联的电影列表，区分`people.douban_id`和`movies.douban_id` |
| `/admin/duplicate_person/confirm_not_same` | POST | `duplicate_id`（重名记录ID）、`person_id1`、`person_id2` | 成功/失败 | 确认不是同一人：将两人`is_duplicate=0`，标记`duplicate_name.is_checked=1`，记录操作人 |
| `/admin/duplicate_person/merge` | POST | `duplicate_id`、`keep_person_id`（保留的人员ID）、`discard_person_id`（废弃的人员ID） | 成功/失败 | 确认是同一人：开启事务<br>1. 废弃人员`is_duplicate=-1`<br>2. 迁移`movie_credits`中所有`person_id=废弃ID`的记录到保留ID（注意联合主键去重，如果已经有相同的关联直接删除废弃的那条）<br>3. 标记`duplicate_name.is_checked=1`，记录操作人 |

## 四、注意事项
1. 所有涉及人员查询的地方自动过滤`is_duplicate != -1`，包括爬虫的`_find_or_create_person`方法、前端人员搜索下拉、列表查询
2. 合并`movie_credits`时注意联合主键`(movie_id, person_id, role_type)`，如果目标人员已经有相同关联，直接删除废弃人员的关联记录即可，避免唯一约束报错
3. 所有写入操作必须加事务，保证数据一致性
4. 严格区分`people.douban_id`（人员豆瓣ID）和`movies.douban_id`（电影豆瓣ID），接口返回和前端展示时不要混淆
